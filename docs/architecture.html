Architecture · Valencia housing market

From listing pages to historized Iceberg tables

An event-driven, serverless lakehouse on AWS. A private collector gathers a snapshot of the market every week. A versioned landing contract hands the data to this public repository, which maintains fourteen Apache Iceberg tables incrementally with DuckDB SQL and reads free-text descriptions with a Claude model. Each stage is started by the data the stage before it wrote, every write can be repeated without harm, and nothing runs between events.

System map

Two repositories, one data lake, one contract between them

Acquisition is private and ends at the landing contract. Everything to the right of the contract is this repository. Both sides write to prefixes of the same S3 bucket; the only thing they share in code is a schema file whose SHA-256 is pinned in tests on both sides.

The flow

One week of data, from the first schedule tick to a labelled listing

The market is walked once a week. There is no weekly job and no orchestrator: a schedule ticks every three hours, and each stage decides from the data whether there is work.

  1. Wake up and check the budget

    private repositorylive

    A schedule fires every three hours, all week. It does not start the collector. It invokes a small gate that reads this week's run reports from the lake and the remaining request budget, and starts a collector only if search areas are still open and budget is left. A week begins on Sunday 00:00 UTC. Once every area is reported complete, nothing starts until the next Sunday, so a finished week costs one short Lambda invocation per tick and writes nothing to the lake.

    Trigger
    EventBridge Scheduler, cron(0 */3 * * ? *)
    Runs on
    AWS Lambda, Python 3.12, arm64
    State
    none of its own: remaining work is derived from the run reports
    Starts
    one ECS task through RunTask, with the schedule time as idempotency token

  2. Collect into Bronze

    private repositorylive

    The collector walks the result pages of each open search area, a municipality or district for sale or for rent. Every listing card it sees becomes an observation. A listing's detail page is fetched once: a DynamoDB table remembers which listings already have their details. That table is a cache and can be rebuilt from Bronze. Each page is stored raw before it is parsed, so a parser fix can replay history. A run is bounded by a request budget and by time, stops on a whole page, and the next tick continues where the reports say it stopped.

    Runs on
    ECS Fargate, ARM64, 0.5 vCPU / 1 GB, public subnet without a NAT gateway
    Built with
    Python, requests, BeautifulSoup, boto3
    Writes
    raw HTML, then Bronze v2 in five prefixes: three record tables as JSON Lines (listing_observations, listing_details, listing_photos), one report per walked area in runs, and one marker per run in _runs, written last. A page the parser rejects goes to a quarantine prefix
    Guarantee
    Bronze objects are written once: S3 conditional PUT with If-None-Match: *

  3. Land the run behind the contract

    private repositorylive

    The run marker's own S3 event starts the landing job. It finds every finished run that has no landing commit yet, reads that run's Bronze with DuckDB, and writes four typed Parquet tables for it: walk, observation, listing_detail and listing_text. The commit, a small JSON object with the schema digest, row counts and the days the run touched, is written last and only once. Everything that needs knowledge of the source ends here: landing has no URL column and a source-neutral schema.

    Trigger
    EventBridge rule on S3 Object Created for the run marker, plus a daily catch-up at 05:00 UTC
    Runs on
    ECS Fargate, ARM64, 1 vCPU / 2 GB
    Built with
    DuckDB: read_json over Bronze, COPY … TO Parquet through httpfs
    Writes
    landing/v3/<table>/run_date=…/run=…/part-0.parquet and landing/v3/_commits/<run_id>.json

  4. Queue exactly one Silver run

    this repositorylive

    The landing commit's S3 event puts a message on a FIFO queue. A Lambda with a reserved concurrency of one consumes it: it adopts a Silver task that is already running or starts one, and waits for its exit code. The message body is never read. It only wakes Silver up, and Silver finds its work itself, so a lost, late or duplicated event cannot cause wrong data. A daily message at 05:30 UTC covers lost events.

    Trigger
    EventBridge rule on Object Created under landing/v3/_commits/
    Runs on
    SQS FIFO with one message group, AWS Lambda consumer
    Why a queue
    PyIceberg rebases a conflicting commit instead of failing, so two overlapping runs must be prevented before they start
    On failure
    the batch is redelivered; after three receives it moves to a dead-letter queue that raises an alarm. A run refused for its input is not retried

  5. Build Silver incrementally

    this repositorylive

    The Silver task subtracts its ingest log from the list of landing commits. For the pending runs it validates every file against the contract, replaces the day partitions they touch, recomputes the listings those days affect, and rewrites the tables of inferred labels. The ingest log is written last. A crash anywhere before that leaves the runs pending, and the rerun writes the same rows.

    Runs on
    ECS Fargate, ARM64, 1 vCPU / 2 GB
    Built with
    DuckDB in memory runs 17 SQL files; Apache Arrow hands the rows to PyIceberg
    Writes
    14 Apache Iceberg tables on S3, registered in the AWS Glue Data Catalog
    Reports
    CloudWatch metrics for pending runs and for feature wordings nobody has classified

  6. Read the descriptions with a language model

    this repositorybuilt and evaluated, deployment open

    When a Silver task exits with code 0, a rule starts the text labeller. It first collects the batches that have ended, then sends the redacted sale descriptions that have no answer yet as one message batch, and exits without waiting. Answers are stored as immutable Parquet, keyed by the SHA-256 of the text and a label version. Silver never calls a model. It joins the stored answers, which keeps a rebuild reproducible and free.

    Trigger
    EventBridge rule on the ECS task state change of the Silver task
    Runs on
    ECS Fargate, ARM64, 0.25 vCPU / 1 GB
    Built with
    the anthropic SDK: Message Batches with structured output, model Claude Haiku 5.5
    Writes
    enrichment/v1/text_label/label_version=…/run=<batch>/part-0.parquet

Beside the weekly flow: reference data

Once a year an operator downloads the census-section boundaries of the national statistics office. A command of this repository converts the file with DuckDB's spatial extension into an immutable vintage with a manifest that names source, licence and the archive's hash. No code fetches third-party data. Silver assigns every listing its section, district and municipality with a point-in-polygon join.

After Silver: Gold and consumers

Not built yet. Gold will hold use-case-specific features and aggregates as plain Parquet under versioned prefixes, so that a browser can read them over HTTP with DuckDB-WASM and no catalog. A training dataset will record the Silver snapshot it was built from.

Data layers

Every input is immutable, every derived layer can be rebuilt

All layers are prefixes of one S3 bucket. The rule that keeps the design simple: inputs are written once and never changed, and Silver is the only layer with history that is maintained in place, inside Iceberg snapshots.

Silver

An incremental run is a set difference, not a watermark

Collection runs can be replayed and can cross midnight, so "everything newer than the last run" would miss corrections to old days. Silver asks a different question: which immutable commits does my own log not hold yet?

  1. List the commits

    One S3 listing of _commits/, and one read of the Iceberg table landing_ingest.

  2. Subtract

    Pending runs are the commits minus the ingest log, by run id. No clock and no stored cursor take part.

  3. Validate before the first write

    Schema digest, column names and types in contract order, row counts against the commit, key uniqueness, the reference vintage and the stored answers.

  4. Replace the touched days

    walk, observation and listing_detail get whole day partitions replaced, each rebuilt from every run that touched that day.

  5. Recompute what those days affect

    listing and listing_text are upserted for the affected listings. Label and history tables are recomputed whole.

  6. Write the ingest log last

    The checkpoint lives in the same catalog as the data. A crash before this step leaves the runs pending, and the rerun produces the same rows.

Deduplication of sightings

Landing keeps every run's rows. Silver keeps one sighting per listing and day: the latest observation, then the latest ingestion, then the later run. A replay that re-derives an old day therefore replaces the original. Padding cards, listings a result page shows from outside the searched area, are kept and flagged, never dropped.

One property behind several listings

Two listings are a certain pair when operation, municipality, rooms, bathrooms and built area are equal, the prices differ by at most 5 %, the coordinates are less than 350 m apart and the floors do not contradict each other. Groups are the connected components of the pairs, found with union-find. The rule is tuned for precision: every judged pair was the same property, and it knowingly misses about a third of the true duplicates.

Disappearance is an observation

A listing has disappeared on the first day its area was walked completely and it was not there. That is recorded as an event, never as a sale or a rental, and a later run can retract it.

Facts and inferred labels stay apart

Quality flags, property groups and model labels live in their own tables with their own versions. A flag never filters a row. A consumer decides what to trust.

Redaction before text is stored

Phone numbers and names after an honorific are replaced in the description before it enters Silver, under a recorded redaction version. Only that redacted text is ever sent to the model.

Lineage on every snapshot

Each Iceberg snapshot carries the landing contract digest, the range of runs it was built from, the transformation version and the redaction version. A training dataset can name the exact rows behind it.

Text labels

A model call is treated as an input, not as a transformation

Renovation state and auctions are stated in the description, not in any typed field. The labeller asks a Claude model once per distinct text and stores the answer. Because the answer is an immutable input like landing, a Silver backfill reproduces the same table without a single paid request.

An evaluation gate before any production run

The prompt, the output schema and the model form one label version. A version goes live only if it reaches a precision of at least 0.90 and a recall of at least 0.80 on a private set of 230 stratified texts. Version tl3 on Claude Haiku 5.5 measured, over three runs, precision 0.99 to 1.00 and recall 0.88 to 0.91 on the weakest label. The reference labels of that set are the reading of a larger model under the same definitions. There is no human ground truth yet, so the figures say how closely the small model follows the large one.

Cost follows the number of new texts

A text is labelled once per label version, whatever number of listings carry it. Batches cost half of direct requests. Measured on the evaluation set: about $0.11 per 1,000 texts, so the whole backlog of roughly 15,600 texts costs under $2 and a normal month well under $1.

No state table

A batch is open while its record file exists and its answer file does not. Pending texts are the descriptions without an answer and outside an open batch. As in Silver, the work list is a set difference over files that are written once.

What leaves the account

Only the redacted description and its hash. The API key is a SecureString in SSM Parameter Store that ECS injects into the container, and the task prints counts, never text. The text does leave AWS and may be processed outside the EU, which the decision record names as an accepted consequence.

Considered and left out

Leaving a tool out is a decision too, and each of these has a recorded reason.

No Spark, EMR or Glue jobs

Three weeks of Bronze were 86 MB, and the five-year projection is about 6.5 million observations. An incremental Silver run takes about a minute on 1 vCPU and a full backfill a few minutes. Iceberg keeps the door open: the same tables are readable by Spark or Athena when one node stops being enough.

No orchestrator

Step Functions was considered and rejected because there is nothing to orchestrate. Each stage is started by the object the previous stage wrote, and each finds its work by a set difference, so order and repetition do not matter.

No prompt or agent framework

The labeller makes one structured request per text. It needs an SDK call, a JSON schema and a validation step, not a framework, a vector store or an agent runtime.

No NAT gateway, no always-on database

Tasks run for minutes a day in a public subnet behind a security group without ingress, which saves about $35 a month. State lives in S3 objects and Iceberg tables, not in a server.

Decisions

Why it is built this way

The decisions that shape the platform, each with what it buys, what was rejected and what it costs. The full reasoning is in the decision records and the feature plans.

Split the platform at a landing contract

Private feature plan; contract in contracts/landing/

Why
The analytics half can be public while acquisition stays private. The contract is a schema file; its SHA-256 is pinned in tests on both sides, so drift fails a build instead of a run.
Instead of
Silver reading Bronze directly, or a shared Python package.
Price
A contract change has to be coordinated across two repositories. A change is a new version beside the old one.

Immutable Bronze, one landing commit per collection run

ADR 0003, supersedes ADR 0002

Why
Files that were rewritten in place forced every reader to guess what had changed: time windows, a lag, a weekly safety run. With write-once objects the question has an exact answer.
Instead of
Day partitions with manifests, the design of ADR 0002, which was corrected three days after it was accepted.
Price
More and smaller files. Compaction of landing is left for later.

Pending work is a set difference; the checkpoint is written last, with the data

ADR 0003

Why
Replays rewrite old days, so a date watermark misses corrections. Commits minus ingest log is correct whatever the order or the number of repetitions.
Instead of
A watermark or a clock, or a checkpoint in DynamoDB that cannot be committed together with the tables.
Price
One listing of the commit prefix per run, a few thousand keys a year.

The data is the trigger

ADR 0003

Why
A stage starts when the object it needs exists. No component has to know the whole pipeline, and a lost event is repaired by a daily catch-up that is harmless when there is nothing to do.
Instead of
Step Functions, a trigger on the previous task stopping, or Lambda as the compute, with its 15-minute limit and a second runtime.
Price
The pipeline has no single picture in a console. Pending-run metrics and alarms replace it.

Silver on Apache Iceberg

ADR 0001

Why
A training dataset pins a snapshot id, and time travel reproduces its exact input. Day partitions are replaced atomically, and a bad run is rolled back to the previous snapshot.
Instead of
Versioned Parquet prefixes, a full copy per model; Delta Lake; S3 Tables, whose managed expiry would remove pinned snapshots.
Price
A catalog dependency, and the duty to expire snapshots, which is still open.

DuckDB SQL on one small Fargate task

ADR 0001, feature plans 001 and 004

Why
Every rule is a SQL file that a reader can run on a laptop against synthetic data. Python only wires files, catalog and checks.
Instead of
Iceberg MERGE through Spark or Athena; an ORM or dataframe layer.
Price
One node's memory is the ceiling. PyIceberg's own upsert failed on composite keys, so the sink deletes and appends inside one transaction.

Serialize Silver runs with a FIFO queue

Feature plan and review 004

Why
The review gate ran a spike and found that PyIceberg retries and rebases a conflicting commit. Two overlapping runs would both succeed and could silently corrupt a table, so overlap is prevented before a task starts.
Instead of
Relying on optimistic concurrency; an S3 lease; a DynamoDB lock.
Price
A Lambda that waits for the task. Three deliveries of 15 minutes put a ceiling of about 45 minutes on one queued run; a backfill is started by hand.

Inferred labels are Silver tables of their own

Feature plans 008 and 013

Why
Judging whether a record is plausible, or which listings are one property, describes the entity itself. Gold stays for datasets that serve one use case.
Instead of
Flag columns on listing, or a Gold dataset.
Price
These tables depend on rows of other days, so they are recomputed whole on every run.

Reference data as immutable vintages

ADR 0004

Why
A vintage names its source, licence and archive hash, and every located row names its vintage. No job depends on a third-party server.
Instead of
A scheduled downloader, a dataset registry, a Python geometry library.
Price
One manual step a year.

Model answers as immutable inputs

ADR 0005

Why
A model call inside a transformation makes every rebuild paid and non-reproducible. Stored answers, keyed by text hash and label version, make the label a join.
Instead of
The labeller writing Silver, which would be a second writer on the catalog; an agent runtime; direct requests at twice the price.
Price
A lag of two runs, and redacted text leaving the AWS account. Amazon Bedrock was evaluated first. The account had no quota there for the model that passed the gate, so the labeller calls the Claude API and the Bedrock adapter remains in the evaluation command.

Synthetic data in every test

Project rules

Why
The repository is public. A seeded generator reproduces the hard cases found in real data: replayed runs, runs across midnight, padding cards, one property listed twice.
Instead of
Sampled real data, or fixtures copied from production.
Price
A new real-world case has to be modelled by hand before it can be tested.

Operations

Failure handling, security and cost

The same facts, sorted by the pillars of the AWS Well-Architected Framework, with the open gaps beside them.

PillarIn placeOpen
Reliability Bronze objects and landing commits are written with S3 conditional writes, so storage refuses an overwrite. Runs are idempotent: whole partitions are replaced and the checkpoint is written last. One run at a time. A dead-letter queue stops a failing message after three receives. Daily catch-ups repair lost events. Iceberg snapshots allow a rollback. Tables of one run are committed one after another, so a reader can see a mixed state while a run is in progress. Object versioning is off on the lake bucket, so a delete is final. A landing commit that breaks the contract blocks every later one until it is repaired by hand.
Security The public pipeline holds no cloud credential; the private one assumes a role through GitHub OIDC that may only push images. Each task role is scoped to its S3 prefixes, one Glue database and one metric namespace. Secrets are SecureStrings that ECS injects. Security groups allow no ingress. Free text is redacted before it is stored or sent. A leak guard in CI keeps private identifiers out of this repository. Tasks have public IP addresses, a cost decision. Encryption uses S3-managed keys, not a customer key. Redaction is two patterns, phone numbers and names after an honorific, and its residue is measured by hand, not per run. No retention period is defined for any layer. The image is pinned by commit tag, not yet by digest.
Operational excellence All resources are Terraform. A runbook covers first deployment, backfill, rollback and the dead-letter queue. Alarms cover pending runs, the dead-letter queue and unknown feature wordings; a task that fails sends mail. Every feature passes a written plan, a review gate and test-first implementation. terraform apply and backfills are manual. The analytics side has one environment. Every alarm depends on a run having happened, so a pipeline that stops starting stays green. Run duration and memory are not recorded, and there is no dashboard.

Limits

Known limits and the work they point to

What this design does not do yet, and what would change first if the data grew by two orders of magnitude.

  • No consistency point across tables.A run is up to fourteen separate Iceberg commits. The ingest log written last makes a crash harmless for the pipeline, but a reader can catch a run halfway, and the snapshot ids that belong together are only printed in the task log. Next: a run manifest written last that consumers and a rollback command read.
  • No table maintenance.Snapshot expiry, compaction and orphan-file removal are not implemented, and every run adds snapshots to every table it rewrites. The policy has to be set before the first training dataset pins a snapshot: tag what is pinned, expire the rest.
  • Work per run follows history, not the change.Only the three fact tables are incremental. Label and history tables are recomputed whole, in an in-memory engine on a 2 GB task whose peak memory nobody measures. That is about a minute today at 23,000 listings. Next: record duration and peak memory per run, set a memory limit with spill to disk, then make the per-listing tables incremental.
  • Silence is not an alarm.Metrics are published by a run. If the queue consumer is left disabled after a backfill, or commits stop arriving, every alarm stays green. The daily catch-up already produces one datapoint a day, so the fix is to treat a day without one as a breach.
  • One lane, no way around a bad commit.Silver processes all pending commits or none. A landing commit that breaks the contract stops every later one, and landing is immutable, so there is no written repair path yet. A healthy run longer than about 45 minutes would also end in the dead-letter queue.
  • Landing v4 is not consumed yet.The acquisition side already writes a fourth contract version beside v3, with four more detail columns. This repository still pins and reads v3, and no feature owns the move.
  • Manual deployment, one environment.Infrastructure is applied by hand from a workstation, and the analytics side has no second environment in which to rehearse a backfill or a new image.
  • The labeller is not in production.Code, tests, Terraform and the evaluation are done; the first deployed batch, the backlog and enabling the start rule are open. Labeller runs are not serialized like Silver runs, and its answer files are protected by a check before the write, not by a conditional write.

Process

How the platform is built

Every feature goes through three stages with a gate between them. The stages are roles played by a coding agent under the author's direction; the gates are files in this repository that a validator checks in CI.

  1. Architect

    Writes a plan with assumptions that are backed by evidence or a throwaway spike, test-first slices, a monthly cost estimate and a cheaper alternative.

  2. Reviewer

    Checks every claim against the repository. Only an approved plan produces the executable task list. The review of the incremental design ran the spike that found the commit-rebase problem and sent the plan back.

  3. Implementer

    One task, one branch, one red-green-refactor cycle, one commit, and edits only in the files the task allows.
